# Repository Structure

## 1. Overview

This document defines the directory structure and organization of the security repositories maintained by **Restudio Official Security updates For OSes**.

The repository structure is designed to support multiple Restudio operating systems, software versions, and security update channels.

The structure may evolve as the infrastructure develops.

## 2. Design Principles

The repository structure follows these principles:

- Clear separation between operating systems.
- Separation between supported versions.
- Dedicated security update repositories.
- Centralized management of public signing keys.
- Protection of repository metadata and package integrity.
- Scalability for future Restudio operating systems.

## 3. Proposed Directory Structure

The following structure represents the intended organization:

```text
Restudio_OSes_Repo/
│
├── README.md
├── SECURITY.md
│
├── docs/
│   ├── security-policy.md
│   ├── update-process.md
│   └── repository-structure.md
│
├── keys/
│   └── restudio-security-public.asc
│
└── repositories/
    │
    └── midwos/
        │
        └── security/
            │
            └── 1.0/
                ├── repodata/
                └── packages/
                    └── noarch/
```

This is a proposed structure. Directories and repository metadata should only be considered operational after they have been created and configured.

## 4. Operating System Separation

Each Restudio operating system should have its own repository directory.

For example:

```text
repositories/
├── midwos/
├── future-os/
└── another-os/
```

This separation prevents packages intended for one operating system from being unintentionally distributed to another.

## 5. Version Separation

Each supported operating system version should have a dedicated repository path.

Example:

```text
repositories/
└── midwos/
    └── security/
        ├── 1.0/
        └── 2.0/
```

This allows security updates to be managed according to the requirements of each operating system release.

## 6. Security Repository Contents

Each RPM-based security repository should contain:

- RPM packages.
- Repository metadata.
- Cryptographic signatures for repository metadata.
- Required package metadata and checksums.

A typical repository may contain:

```text
security/
└── 1.0/
    ├── repodata/
    │   ├── repomd.xml
    │   └── repomd.xml.asc
    │
    └── packages/
        └── noarch/
            └── example-package.rpm
```

The actual metadata files and directory layout are generated by the repository management tools.

The example above illustrates the intended organization, not a manually maintained metadata format.

## 7. Public Signing Keys

Public signing keys should be maintained separately from private signing keys.

The `keys/` directory is intended to contain public keys used by clients to verify official packages and repository metadata.

Example:

```text
keys/
└── restudio-security-public.asc
```

Private signing keys must never be uploaded to public repositories, included in operating system images, or distributed to clients.

Public keys must be distributed through trusted official channels, and their fingerprints should be independently verifiable.

## 8. Repository Metadata

Repository metadata is essential for RPM-based package management systems.

For the Restudio infrastructure:

- Metadata must accurately describe available packages.
- Metadata integrity must be protected.
- Repository metadata signatures must be verifiable.
- Clients must be configured to require appropriate signature verification.

RPM package signatures and repository metadata signatures serve different purposes. Both are required for the intended verification model.

## 9. Repository Compatibility

Repository configuration must be appropriate for the target operating system and its package management tools.

For MidwOS, the intended package management foundation is RPM with Zypper and libzypp.

Repository definitions should specify the correct operating system version and security repository location.

## 10. Future Expansion

The repository infrastructure may support additional features in the future, including:

- Multiple security update channels.
- Additional Restudio operating systems.
- Separate architecture-specific package directories.
- Security advisory archives.
- Repository retention and archival policies.

These features should be introduced only when their implementation and maintenance requirements are defined.
